01 · The brief

Two pieces, joined at one point

WordPress

An editor logs in and assembles a page by picking blocks from a library. Publishing a page must not require a developer.

React

TypeScript, bundled by Vite, styled with Tailwind, rendered on the server. It reads WordPress over an API and turns those blocks into components.

The brief named the interesting part itself: the seam between the two, how a block chosen in a back office becomes a typed component with the right props, and how that holds up when the content changes. Everything else in the exercise exists to make that seam visible.

Ground rules that shaped the work

  • Server rendering was mandatory. Next.js was excluded because it brings its own bundler; Vite's own SSR was permitted.
  • AI assistants allowed, but you must be able to explain any file. So: no generated boilerplate, and nothing shipped that could not be defended line by line.
  • Starters and plugins are fine, if listed. Which is why the inventory on slide 12 exists.

02 · The seam

Why this is the hard part

WordPress does not store a page as data. It stores it as one string of HTML, with the structure hidden in comments: 

<!-- wp:cover {"url":"…","dimRatio":62} -->
<div class="wp-block-cover">
  …<h1>Heading</h1><p>Sub</p>…
</div>
<!-- /wp:cover -->

A front end handed that string has two options: echo it as HTML, or scrape it. Neither gets you a component with the right props.

The translation therefore happens in WordPress, not in React.

A small plugin reads WordPress's own parsed block tree (the same structure the block editor already understands) narrows it to the types this front end can draw, and republishes it as real fields.

The React side never sees HTML-with-comments. By the time it is involved, the question “what is this block?” has already been answered.

03 · Architecture

Four parts

Content

WordPress 7.1

Runs in Docker on :8080, with MySQL 8 and phpMyAdmin alongside. Holds every page and image. The editor only ever sees this.

The seam

headless-blocks

A plugin written for this project. Two classes: a parser that turns the block tree into typed payloads, and a schema that publishes them over GraphQL.

The contract

WPGraphQL 2.23

Free plugin from wordpress.org. Provides the endpoint and the type registry the custom block union plugs into. No premium add-ons anywhere in this build.

The renderer

React 19 + Vite 8

Server-rendered on :3000. Fetches, validates, and draws. Nothing about it knows WordPress exists beyond an HTTP endpoint.

04 · The path

One block's journey

  1. 1
    An editor picks a Cover block In the ordinary Gutenberg editor. No custom UI, no proprietary page builder.
  2. 2
    WordPress stores it As HTML with block comments, in post_content, exactly as it would for any theme.
  3. 3
    The parser reads the block tree parse_blocks(), then narrowed to the five types this site can draw.
  4. 4
    GraphQL answers with a union Each block tagged with the type it should resolve to. Unknown types are reported, not dropped.
  5. 5
    The server fetches during SSR Before any HTML leaves the building. The browser never calls WordPress.
  6. 6
    Zod parses each block Against the schema. Anything that does not match is dropped and reported, not rendered.
  7. 7
    The renderer switches on the type One case per block, narrowing to exactly the right props. A missing case is a compile error.

05 · The contract

A GraphQL union, not one loose type

union ContentBlock =
    HeroBlock
  | HeadingBlock
  | RichTextBlock
  | ImageTextBlock
  | CallToActionBlock

Every renderable block is its own object type with its own fields, joined by a union. The alternative (a single Block type with a type string and every field optional) merely moves the problem to the consumer, where each component must decide for itself which fields it can trust.

With a union the question is settled by the schema, and it mirrors the TypeScript union member for member.

Why not the REST API?

  • REST returns rendered HTML for content. Block structure arrives as one string, so the typed seam has to be reconstructed by scraping: the problem moved to the wrong side.
  • A union is expressible in GraphQL. The contract was the thing being graded, and GraphQL can actually state it.
  • The schema is introspectable. The front end's contract can be inspected rather than agreed in a wiki page.
  • _fields is not a substitute. Trimming REST responses controls size, not structure.

Cost: a plugin dependency and a query language. For a page built from typed blocks, that is the right trade.

06 · Types

The data is parsed, not trusted

WordPress can gain a field, lose one, or send a value nobody expected. None of that may reach a component. The schema is the contract, and it is the only definition: the types are derived from it rather than declared beside it. 

export const blockSchema = z.discriminatedUnion('__typename', [
  heroBlockSchema,
  headingBlockSchema,
  richTextBlockSchema,
  imageTextBlockSchema,
  callToActionBlockSchema,
]);

export type Block = z.infer<typeof blockSchema>;
export type BlockOf<T extends BlockType> =
  Extract<Block, { __typename: T }>;

One definition

Types come from the validator, so a type declaration cannot drift away from its schema.

Narrowing for free

BlockOf<'HeroBlock'> gives a component the hero's props and nothing else, with no cast anywhere.

Failures are visible

A block that fails validation is dropped and reported. Silent omission is the failure mode worth designing against.

07 · Extending it

Adding a block type is compiler-enforced

1

Register the type

In the plugin: a handler in Block_Parser, then the type in the schema's union.

2

Add it to the union

One entry in blockSchema, plus one inline fragment in the GraphQL query, without which the block arrives with no fields.

3

Add a component and a case

In the renderer's switch statement.

Step 3 cannot be forgotten. The renderer ends with this:

default: {
  // Assigning to `never` performs the check: if a block type were
  // missed, `block` would not be `never` and this would not compile.
  const unhandled: never = block;
  void unhandled;

  return null;
}

The failure is at build time rather than a blank space on a page. That is the whole point of the exercise expressed as four lines of TypeScript.

08 · Failure

What happens when the content is wrong

The realistic failure in a headless setup is not a crash. It is quiet omission: an editor adds a block, the front end has no component for it, and the content is simply absent. Nobody notices for a month. All three ways that can happen are handled, and all three are visible.

Failure modes and how each is handled
Situation What happens Where it shows
A block type this front end has no component for The inserter does not offer it; if it arrives anyway, the parser skips it and the page renders normally skippedBlocks in GraphQL, and the on-page content notice
A supported block with nothing in it Left out. The block is still sitting in the editor looking perfectly fine, so this is the one that reads as a bug omittedBlocks in GraphQL, and the content notice
A block claiming a known type that fails validation Dropped by Zod; every other block still renders The content notice, and the server log

None of them takes the page down. All are visible. The block inserter is also restricted to the renderable library, so the first case is now prevented rather than reported: an editor cannot insert a block the front end will not draw. The seeded Home page still carries a core/list block on purpose, so the reporting stays demonstrable rather than merely claimed.

The on-page notice is scaffolding for this exercise. In a real project the same information belongs in CI, failing the build when WordPress and the front end disagree.

09 · Rendering

Server rendering, and what it buys

The visitor receives a complete document. Not a shell waiting for JavaScript to fill it in.

  • The first paint does not wait on WordPress. The database round trip happens on the server, not on the visitor's connection.
  • The head is correct before anything renders. Title, description and preview image are derived on the server from content the browser has not seen yet. Link previews and crawlers see real content.
  • Unknown paths are real 404s. A friendly “not found” page served with a 200 tells search engines the page exists.

Hydration, not re-rendering.

The validated data is serialised into the document, so the browser adopts the markup already on screen instead of fetching again. Re-fetching would open a window in which the two renders could disagree.

One detail worth knowing: the serialised JSON has its < characters escaped, because a string containing </script> would otherwise close the tag early and break the document.

10 · Evidence

What was actually verified

  • True server rendering. 7.3 KB of HTML containing the headline, hero image, stylesheet link and embedded data, all present before any JavaScript runs.
  • Clean hydration. Zero console errors, zero failed requests, in both development and production builds.
  • The build is clean. Type checking and the production build both pass; the production server was run and checked separately from the dev server.
  • Five block types round-trip correctly, with the unsupported block reported as skipped.
  • Publishing needs no developer. A page created in WordPress appeared at its own address and added itself to the navigation, with no code written and nothing deployed.

Three real bugs found and fixed

  1. The image came back empty. Media & Text stores its attachment as mediaId; Cover stores it as id. Reading only id silently degraded the image to a bare URL with no dimensions and no alt text. It still looked plausible.
  2. A heading rendered twice. The heading lives inside the content column, so it arrived both as its own field and inside the body HTML.
  3. A block authored in the editor parsed as empty. For a block that contains other blocks, innerHTML holds only the markup around the nested content, which lives in innerBlocks. An editor-authored Media & Text block arrived with an empty content column, so the parser dropped it as “nothing to render”. The seed content hid this: it writes the heading and paragraph inline, the one shape where innerHTML happens to be complete.

12 · Honesty

Where it stopped

Working end to end and verified: WordPress → plugin → GraphQL union → Zod → typed components → server-rendered HTML → hydration. Three seeded pages, five block types, unknown blocks reported, production build serving real HTML.

Not done, in the order it would be done next:

  1. Generated TypeScript types. The schema could be introspected and the union generated from it, so WordPress is the single source of truth rather than the Zod file mirroring it by hand.
  2. Graceful rendering for unknown blocks. Currently skipped with a notice; a placeholder that renders the block's text would be better for a real site.
  3. Caching. Every request queries WordPress. A short-lived cache keyed by path, or static generation for pages that rarely change, removes that.
  4. Navigation from a WordPress menu rather than from the list of published pages, so ordering and nesting belong to the editor.
  5. Tests. The parser is the piece with real logic in it, and the one a test would pay for: feed it block markup, assert the payload.
  6. A media proxy. Images are served from one origin and the app from another; in production those would be one origin.

13 · Reproducing it

Running it

Requirement: Docker Desktop. Nothing else: no Node, no PHP, no MySQL. 

# One command does the lot: containers, WordPress, plugins, content, build
bash .devcontainer/setup.sh
# Then open http://localhost:3000

# The same thing by hand:
cp .env.example .env
docker compose up -d --build

docker compose run --rm wpcli core install \
  --url="http://localhost:8080" --title="Boien Reyes" \
  --admin_user=admin --admin_password=admin \
  --admin_email=admin@example.com --skip-email
docker compose run --rm wpcli plugin install wp-graphql --activate
docker compose run --rm wpcli plugin activate headless-blocks
docker compose run --rm wpcli plugin activate headless-redirect

docker compose run --rm wpcli eval-file /seed/seed.php

The credentials above are throwaway values for a container bound to localhost. They are not secrets, and they are not for anything else.
